# Wi-Fi DNS 路径：已确认的旁路与离线配置分析

2026-10-26。没有硬件访问、网络请求或配置写入。本轮没有修改 native WireGuard 源码，也没有解决 DNS 旁路；新增的是可复现的固件分析和后续实现依据。

## 为什么网页能打开仍不足以证明完整 VPN

`rekey-pressure/native.c` 的 `intercept()` 与 `forward()` 都先检查 IPv4 目的地址：与 `LAN_GATEWAY` 前三个字节相同就返回原厂路径。这是固定 `/24` 判断，不是读取当前 DHCP 子网掩码。因此客户端向网关发送 UDP/TCP 53 请求时，包不会进入这个 WireGuard 加密路径。该提前返回也在实验到期检查之前。

外部 IPv4 DNS 目的地址可以进入现有 WireGuard 路径，但仍受单客户端、会话状态、长度和协议等检查限制。这里是源码分析，不能把它写成新做过的 DNS 实机验收。网关收到查询后如何发出上游请求也没有在本轮抓包验证。

之前 HTTPS、ping、指定地址的 DNS 查询成功，不能证明“使用默认 DHCP 设置的 Wi-Fi 客户端，其 DNS 也走隧道”。切断 DNS 会导致上网失败；这也不算完成目标。

## 精确固件中的 DHCP 配置结构

对所有者本地 DSP2 原始代码、只读数据和初始化数据先核对完整 SHA-256，随后检查17个字符串、71个指令地址和2个数据表项。脚本从已校验代码生成临时 ELF，结束后删除；不依赖可能过期的分析 ELF。最新结果见 [dhcp-dns-consumer-static.json](../outputs/uv310-wireguard/evidence/dhcp-dns-consumer-static.json)。最初尚未连接消费者时的 [dhcp-dns-static.json](../outputs/uv310-wireguard/evidence/dhcp-dns-static.json) 保留为历史证据。

| 对象 | 地址 / 偏移 | 静态发现 |
|---|---|---|
| DHCP 文件生成函数 | `0xf73e60` | 打开 `/etc/udhcpd.conf`，包含 `option dns %s` 格式 |
| 输入结构 | 104字节 | 网关 `+0x08`、掩码 `+0x18`、池起止 `+0x28/+0x38` |
| DNS 字段 | `+0x48`、`+0x58` | 两个字符串槽，间隔16字节；非空时输出，均空时回退到网关 |
| Web `DHCP_SET` handler | `0x1833fc0` | 读取 LAN IP、掩码、DHCP模式、地址池、租期；清零104字节结构后没有填写 DNS 两个槽 |
| 内部消息构造函数 | `0x182e6cc` | 类型 `0x50`，复制104字节到消息 `+0x1f0` 后提交 |
| 初始化路径 | `0x13cf228` | 解析已有 DHCP 配置；所检查的有效配置分支还要求第一个 DNS 字段非空；默认分支填入网关作为 DNS |
| DNS 代理配置生成函数 | `0xf73fe4` | 输出 `resolv-file=/etc/resolv.conf`，这是上游解析配置线索 |

结构布局是根据读写地址及格式串人工推导；指令锚点只是保证所审核输入没有漂移，不是自动数据流证明。Hexagon 同一 packet 的普通寄存器操作数读取旧值，分析时不能当成逐行顺序执行。

**后续已接上静态调用链：** `0x182e450` 向队列 `0x2f02c7c` 提交消息；分发器在 `0x182eb60` 判断类型 `0x50`，调用消费者 `0x182f378`。消费者复制消息 `+0x1f0` 的104字节到栈上，经 `0x182f39c` 跳转到 DHCP 写入函数 `0xf73e60`。之前只搜索直接 `call 0xf73e60` 会漏掉这个通过 `r28` 跳转的入口。`0x50` 是固件内部消息类型，与 DHCP 网络报文的 DNS 选项码6不是同一层协议。

DHCP 服务入口 `0xd7d16c` 有 `udhcpd_main` 日志标记，并在 `0xd7d1b4` 把同名 `/etc/udhcpd.conf` 交给解析函数 `0xde6f84`。配置表项 `0x1982308` 将 `option` 交给 `0xde732c`，对应 option 链表指针位置为 `0x338d520`。初始化数据中的 `0x1b155dc` 表项把 `dns` 映射为选项码6、flags `0x31`；解析器检查其列表标志，支持逐项追加。这里是固件自身的解析关系，不只是根据文件名猜测。

**仍然没有实机证明：** 上述服务当前正在运行、修改后会重新加载、DHCP ACK 确实下发新 DNS、配置掉电后保留。网页 handler 取得的成功结果是消息构造/入队结果；消费者的文件写入返回值没有通过这条路径反馈给原网页请求。HTTP 成功提示不能作为 DNS 已生效的验收依据。

固件可能保留多个平台的代码。发现 `/etc`、dnsmasq 或类似 shell 的字符串，仍不能据此宣布存在可登录的 Linux 用户环境。

已保存的 `dhcp_setting.asp` 页面没有 DNS 输入字段；成功回调还有 `device_reboot` 请求。该页面不作为无副作用的探测入口。本轮没有调用页面或重启。

## 下一条实现路线

优先调查**设备 DHCP 下发隧道可达的 DNS 地址**：客户端后续直接向该地址查询，便可使用现有外部 IPv4 转发路径，避免在 BCM43362 上立即增加 DNS 流映射表。此方案尚未证明可配置，不能直接给用户一条“已经有效”的设置命令。

1. 消费者到文件写入、服务启动到文件读取的静态路径已找到；下一步确认可用的字段设置入口和重载方式。当前 Web handler 没有 DNS 参数，不能靠往 POST 中增加猜测的字段名完成。也不能把内部函数地址当成可从 WebUSB 直接调用的 API。
2. 区分“给客户端下发 DNS”与“修改网关代理的上游 DNS”。只改 `dns_mode`、`prefer_dns_manual` 等名字相似的配置，不能证明前者生效；网关自行发出的流量未被本 Wi-Fi 截获点证明覆盖。
3. 硬件回来后先保持原厂基线，抓 DHCP ACK 的 DNS 选项，再考虑最小可恢复修改。需验证重新租约及冷启动是否仍生效。
4. 若原厂 DHCP 字段无法通过已有入口配置，优先评估在已经能执行代码的 BCM Wi-Fi 路径改写 DHCP ACK 中的 DNS，再评估网关 DNS 的透明代理。前者必须有界解析 DHCP option（包括 overload）、处理包长/分片/UDP checksum，并定义缺少 DNS 选项时的行为；不能用固定偏移改包。透明代理须正确处理回程源地址、UDP/TCP、端口冲突、超时、分片与 checksum；不能只把目的 IP 改掉。新增 RAM 与处理延迟须计入目前紧张的内存预算。

给单台手机手动设置外部 DNS 可用于隔离验证，但不作为最终“所有 Wi-Fi 客户端直接可用”的交付方案。下发 DNS 也不能独自保证没有旁路：手动使用网关/其他 LAN DNS 的请求仍需明确的代理或阻断策略；LAN 管理访问、IPv6、多个客户端仍需分别解决。

## 实机验收条件

- DHCP ACK 中确实下发预期 DNS，客户端默认设置下取得该地址；不能只读取网页配置值。
- 使用随机查询名避免缓存，分别验证 UDP 与 TCP DNS，以及正常网页解析。
- 在隧道对端确认相应内层 DNS 请求；同时观察原有 WAN 路径是否出现同一测试查询。设备内计数与对端证据结合，避免把主机 VPN 当作结果。
- 隧道断开或密钥过期时，相关外部 DNS 不回落到明文路径；恢复后重新可用。
- 默认 DNS、手动 LAN DNS、外部 DNS、IPv6 DNS 和多客户端各自有明确结果。跨换钥、DHCP 续租和重启后重复。

这些条件目前均不能由本次静态审计宣告通过。

## 离线复现

需要所有者自己的三个匹配固件段；公开仓库不提供厂商固件或用户配置。脚本只有 Python 标准库依赖，另需支持 Hexagon 的 LLVM objdump。`--out` 不覆盖已有证据。

```sh
python3 tools/audit_dhcp_dns.py \
  --code /path/to/private/dsp2-code.bin \
  --rodata /path/to/private/dsp2-rodata.bin \
  --data /path/to/private/dsp2-data.bin \
  --objdump /path/to/llvm-objdump \
  --out /tmp/uv310-dhcp-dns-new.json
```

本机验证：匹配固件的17个字符串、71个指令锚点及2个表项全部匹配；三个输入段分别换为错误固件均在反汇编前被拒绝；已有报告被拒绝覆盖；故意修改指令预期值会被检查发现。共5项审计工具防错检查。这些检查不执行 DHCP 服务。公开 CI 不拥有私有固件，因此不执行这项固件审计；现有 QEMU CI 通过也不证明本页描述的 DNS 路径已修复。
