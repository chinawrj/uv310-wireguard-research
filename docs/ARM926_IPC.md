# ARM926：USB 包通路、跨核 IPC 与 WireGuard 的边界

2026-10-28，离线静态逆向。本轮只读所有者已有 AMSS ELF，没有访问网卡、内网服务或写入固件。**已经找到 ARM 内实质的 USB ECM 包收发适配代码和回调注册；尚未打通 ARM 与 DSP2/Wi-Fi 的包交换，也没有可调用的 ARM UDP socket API。** 因此 ARM 值得继续调查，但现在不能据此替代 M3 主线或声称 WireGuard 已能在 ARM 上接管 Wi-Fi。

与 [ARM926_IMAGE_MAP.md](ARM926_IMAGE_MAP.md)、[ARM926_RUNTIME.md](ARM926_RUNTIME.md)、[DSP2_API.md](DSP2_API.md)、[DSP_ROLES.md](DSP_ROLES.md) 联读。下面所有地址是此 ELF 的虚拟地址，函数体采用 Thumb；函数指针最低位为 1。它们不是跨版本稳定 API，不能把这些地址直接作为下载器中的调用地址。

## 证据范围和复核

唯一分析对象 `amss.elf` 的 SHA256：

```
388dda0d44c9ed391306c8dbd5851a612b0e68c3dc7faec189234dd7a525c9f5
```

公开材料为派生接口事实、少量指令断言和诊断锚点，不包含原始 ELF、连续反汇编或真实配置。复核脚本 [ipc.py](../work/uv310-wireguard/arm926-audit/ipc.py) 先核验整文件哈希，再读取 ELF32 PT_LOAD 段；哈希不符立即拒绝。输出 [arm926-ipc.json](../outputs/uv310-wireguard/evidence/arm926-ipc.json)。本轮 **78 个指定锚点检查通过**，它们验证所列事实在该文件内存在，不是硬件功能测试或全镜像反编译覆盖率。

在仓库根目录，对所有者自己保管的镜像执行：

```sh
python3 -m pip install capstone
python3 work/uv310-wireguard/arm926-audit/ipc.py \
  --amss /absolute/private/path/amss.elf \
  --output /tmp/arm926-ipc.json
```

脚本只读镜像，写派生 JSON，不打开设备或网络。Capstone 用于指定 Thumb 指令检查。不要以线性反汇编的“可解码比例”推断代码边界：同一段里存在字面量池、诊断表和字符串。

## 1. 已证实的 ARM USB ECM 路径

这不是只有 `ECM` 字符串的判断。诊断记录、PC 相对加载、函数内 DSM 字段操作和回调注册可以互相对齐：

| 作用 | Thumb 函数体/关键位置 | 证据与边界 |
|---|---|---|
| ECM data open | `0x002d11c8` | `0x002d11d2` 加载诊断记录 `0x002e49d8`，其字符串为 `hsu_al_ecm_data_open(): Enter`；之后校验和分配实例、保存应用参数。 |
| USB RX 完成回调包装 | `0x002d0414`，指针 `0x002d0415` | `0x002d0428` 调用下面内部函数。初始化代码 `0x002d0aac–0x002d0aae` 把它装到回调表 `+0x18`。 |
| USB RX 内部处理 | `0x002d020e` | `0x002d0366` → 字面量 `0x002d0410` → 记录 `0x002e4810` → `_ecm_rx_done_internal` 日志。循环处理各传输状态/长度、更新 DSM 链和统计。 |
| RX 应用交付 helper | `0x002d0188` | 从 DSM `+0x18` 取实例，选择实例 `+0x1120` 回调或 `+0x1118` 队列；都不可用时走清理路径。 |
| 应用提交 USB TX | `0x002d15c4` | 记录 `0x002e4b4c` 标明 `hsu_al_ecm_data_transmit`；消费 DSM 包，排队或提交下层；错误分支会清理。 |
| USB TX 完成回调 | `0x002d0430`，指针 `0x002d0431` | `0x002d04bc` → 字面量 `0x002d0720` → 记录 `0x002e4858` → `_ecm_tx_done` 日志。初始化 `0x002d0ab2–0x002d0ab4` 装到回调表 `+0x20`。 |

还有上一级注册证据：`0x0023c864/0x0023c866` 将 `data_open` 的 Thumb 指针 `0x002d11c9` 放入临时注册结构 `+0x10`；`0x0023c870/0x0023c872` 把 `data_transmit` 指针 `0x002d15c5` 放入 `+0x1c`，之后经 `0x0023c898` 的间接调用提交。同一段重复注册多个数值端口；其枚举命名和真实调用者仍未恢复。因此下一步应沿注册中心反查调用者，而不是只搜直接 `BL data_open`。

RX/TX 方向以 **USB 设备端** 为准：RX 是 USB 主机发到网卡；TX 是网卡发到 USB 主机。它们不能直接等同于 Wi-Fi 上/下行或者蜂窝上/下行。

可复核的局部数据流：

```text
USB 驱动完成表 +0x18
  → 0x2d0414 → 0x2d020e
  → 0x2d00a8：分拆/检查接收 DSM 链
  → 0x2313f2：排入 0x441874 队列，向 0x440cd4 发信号值 4
  → 工作循环 0x23137a/0x231380
  → 0x2d0188
      → 实例 +0x1120 回调(&DSM)
      → 或实例 +0x1118 队列
      → 或清理 DSM

应用传入 DSM
  → 0x2d15c4
      → 实例 +0x111c TX 队列
      → 或 0x2d0ee0 下层提交候选
  → USB 驱动完成表 +0x20
  → 0x2d0430：清理已完成项，保留剩余链
```

其中队列/信号函数名是行为推断，不是恢复了符号表。工作循环存在证明回调并非简单从任意上下文同步调用；实际任务名称、优先级、锁和延迟仍需完整核对。

### 1.1 数据结构与参数的可用部分

`hsu_al_ecm_data_open` 的输入指针保存在 `r5`；正常非 SPS 分支有下列复制关系：

| 输入参数偏移 | 实例内偏移 | 已观察用途 |
|---|---|---|
| `open +0x04` | `context +0x1118` | RX 队列候选，RX helper 无直接回调时使用。 |
| `open +0x08` | `context +0x111c` | TX 队列候选，data_transmit 路径排队时使用。 |
| `open +0x14` | `context +0x1120` | RX 回调函数指针；调用时 `r0` 指向栈内 DSM 指针槽，即候选 `callback(dsm_item **item)`。 |

复制指令位于 `0x002d1350–0x002d135e`。另一分支 `0x002d1346–0x002d134a` 将三者清零；不能跳过模式与实例状态检查就注册回调。

实例分配例程 `0x002d0784` 使用候选基址 `0x0049265c`、步长 `0x1190`、最多 5 个槽（循环和字面量推断）。这不是“5 个可供应用随意使用的网络接口”，也没有实机确认哪个槽当前存在。

DSM 局部结构：

| 偏移 | 字段证据 | 使用限制 |
|---|---|---|
| `+0x08` | `pkt_ptr`/包链后继候选；RX、TX 循环读取并切断链。 | 不要据此认为所有 DSM 内部链都只用这个字段。 |
| `+0x10` | `data_ptr`，由 TX 日志与相邻读取指令互证。 | 包内存归原厂 DSM 分配器；不能换成普通 malloc 指针。 |
| `+0x18` | `app_ptr`；RX 交付前保存 ECM 实例，TX 可携带另外的辅助对象。 | **不同路径语义不同**。TX 完成路径会对非零值调用 `0x002a0356` 并清零；不能统一当成永久 context。 |
| `+0x22` | `uint16_t used`/有效数据长度候选；RX 将完成长度写入该位置。 | DSM 容量、头部预留、链中帧边界仍未完整恢复。 |

RX 内部函数可观察到传输状态数组、长度数组、数量、实例参数；长度来自 `r2` 指向的 32 位数组，状态字节来自原始 `r0` 指向的数组，`r3` 为处理数量。公开回调完整 C 原型尚未恢复，不把这张表当编译可用的 SDK。

`data_transmit` 入口保存 `r0/r1/r2`，其中 `r0` 经 `0x002d13cc` 查找实例，`r2` 保存为后续 DSM 链参数；`r1` 的具体意义本轮未确认。它既可能排队，也可能走清理，不能假设调用返回之后调用方仍持有原包。

### 1.2 所有权、同步和模式限制

以下细节决定了后续能否安全接入 WireGuard：

- RX 交付先拆链再入工作队列；`0x002d0188` 把 **DSM 指针的地址** 传给回调/队列函数。指针可能被消费或改写，不能保留栈地址。
- data_transmit 在实例状态错误、禁用、SPS 分支调用 `0x00291a00` 清理候选；正常分支也可能将 DSM 交给队列或下层。应按“可能转移所有权”处理，直至分配/释放 ABI 被逐项证明。
- TX 完成在 `0x002d055a–0x002d057e` 切断已完成链、清理并留下剩余链。不能无视部分完成、取消和错误就复用缓冲。
- 日志和分支明确区分 SPS 模式。此处恢复的是经过 DSM 软件路径的分支；即使这些代码存在，实际运行模式也可能绕过它。
- 本轮没有确认 `0x00291a00`、`0x002341f2` 等所有 callee 的完整 ABI，文中“清理/队列”依据调用上下文与诊断。没有因此发布直接调用补丁。

## 2. SMD/SMEM/ONCRPC：有 IPC 设施，不等于已得到网络 API

| 子系统 | AMSS 内锚点 | 可以确认 | 仍不能确认 |
|---|---|---|---|
| SMD packet memcpy | 元数据 `0x2001f950/0x2001f960/0x2001f970`，源文件字符串 `0x001f1768` | RX 剩余字节断言、RX/TX 状态错误记录，说明镜像含 packet memcpy 实现相关设施。 | channel ID、哪一端是 DSP2、共享环地址、是否承载 Wi-Fi/IP 包。 |
| SMD bridge server | 元数据 `0x200217a0/0x200217b0`，源文件字符串 `0x001f1872` | 端口连接与命令分派诊断；控制层确实存在。 | 正常消息格式、可用端口、权限、控制消息能否送真实数据。 |
| SMEM | 字符串 `0x20001b9b`、`0x20001c72`、`0x20011bb6` | 分配指针、布局一致性、block port SMEM 分配错误锚点。 | 分配表位置、item ID、cache 属性、跨核内存屏障、生产者/消费者方向。 |
| ONCRPC pacmark | 函数候选 `0x00237100`，日志记录 `0x002e4ffc` | 构造传输头，调用下层虚表写方法并检查实际写入长度；失败日志是 `unable to write packet`。 | IP socket、UDP、网络接口或蜂窝出口。这个 packet 是 RPC 传输单元，不能直接当 IP 包。 |

ONCRPC 具体例子：`0x00237134–0x0023713e` 从对象 `+0x0c` 获取传输对象，再从其 `+8` 获取虚表，调用虚表 `+8` 方法，参数为传输对象、缓冲、长度；随后还有虚表 `+0x14` 方法调用。这里只恢复了传输封装边界，尚未追到最终 SMD/端点实现，不能把它命名为 `sendto()`。

SMD 的记录是**元数据**，例如 `0x2001f960` 的前两字是诊断文本和文件名指针；不是函数表。类似地，ECM 诊断记录中的第一个字形如 `0x002a0a79`，不能因数值落在可执行映射范围就把它当代码地址。本轮通过 PC 相对加载和真实函数边界寻找 caller，避免此类误判。

没有利用某字符串搜索不到就声称功能不存在；本轮尚未建立 socket API，不代表镜像绝无 socket 代理。SMD/SMEM 名字也不允许套用 Android 内核里另一型号的 ABI。

## 3. 对“WireGuard 放 ARM926”的判断

已证实的有利条件：ARM AMSS 内有 USB 网络数据适配层、DSM 包对象、接收交付回调/队列以及发送路径，说明 ARM 不是只有启动代码和控制日志。

未解决的必要条件：

1. **Wi-Fi 客户端流量能否交给 ARM。** DSP2 的 DHD/IPnet 收发已在另文定位，但尚没有证据连接到上述 ECM 队列。改 USB ECM 不会自动改变 Wi-Fi 转发。
2. **WireGuard 外层 UDP 的出口/回程。** 需要 DSP2 网络栈代理、可验证的原始包通道，或 ARM 自己的 IP/UDP 栈；本轮未识别完成任一路线。
3. **正常运行时入口。** 在 USB 下载器中运行 ARM applet 不等于可在 AMSS 正常运行时附加任务。不能为了 Hello World 或 WG 停掉 modem/原厂服务。
4. **跨核所有权与吞吐。** 若走 ARM↔DSP2，需要缓冲归属、队列背压、cache 同步、定时器、MTU 与错误恢复；只有 SMD 名字不够。
5. **资源与生命周期。** 可用 RAM、栈、CPU 余量、任务优先级、熵源和 WireGuard 握手/换钥时间源没有验收。

因此当前合理表述为：**ARM926 是可继续调查的执行位置，已有 USB 软件包通路证据；“Wi-Fi 经 ARM 原生 WireGuard”仍处于未打通的数据路径阶段。** 不提供性能猜测，也不把 USB 包处理能力外推为蜂窝或 Wi-Fi 吞吐。

## 4. 下一步最小实验

硬件仍不需要回来即可做：

1. 以 `hsu_al_ecm_data_open(0x2d11c8)` 的实际注册/caller 为种子，恢复 `open+4/+8/+0x14` 是由谁填入。追踪它们最终走向 SMD、路由服务还是另一应用，优先补“实例 RX 回调是谁”的具体地址。
2. 对照 DSP2 映像中的 SMD/共享内存元数据，尝试匹配**双方** channel 名、枚举值、队列尺寸和握手字段；只有单边字符串时不命名为 ARM↔DSP2 数据口。
3. 为 `0x2d0188` 建一个隔离仿真夹具：只用合成 DSM/context，回调替换为记录器；分别检查 callback、队列、无消费者三分支。此实验最多证明局部控制流/指针变更，不证明真实网络。
4. 单独恢复 TX 的分配、部分完成和错误回收 contract，再考虑任何原生接入代码。

未来用户恢复硬件并授权时，最小实机验证应是读取现有实例/回调状态与计数，并用一帧合成 USB 流量核对上述分支是否运行；先不改 Wi-Fi 路由或注入 WireGuard。只有映射到真实生产者和消费者之后，才设计可撤销的数据处理 hook。
