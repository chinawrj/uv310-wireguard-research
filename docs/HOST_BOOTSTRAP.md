# 主机引导的半成品方案

2026-10-28，按用户新选择：允许主机参与引导，目标仍是UV310内部执行WireGuard并转发其Wi-Fi客户端流量。自主冷启动不再是这个半成品版本的前置条件；它保留为后续目标。当前没有硬件，以下部署阶段是待实现/验收设计，不能作为已成功的操作指南。

## 运行结构

```text
主机：配置保管 + 每次引导的新随机材料/时间 + 编译预检 + USB部署与恢复 + 状态观察
                                              |
                                              | USB控制面
                                              v
Wi-Fi客户端 → UV310内部WireGuard → UV310蜂窝出口 → WireGuard服务器 → 目标网络
```

主机不运行代替设备的VPN，不承担Wi-Fi业务数据转发。主机必须在启动/重新引导时可用；运行时是否能移走主机还取决于供电方式和实机行为，目前不能保证。持续插着USB不等于业务经过主机。

## 第一版能力与限制

采用独立`rekey-dns-observe`候选与`control-icf`构建，单IPv4客户端、有界实验，包含N1诊断协议。现有256B合成池布局仍有256B历史地址余量，但真实私有配置必须重新链接审计，不能照搬这个数值。当前实验deadline为360000个cached ticks；不能用模拟时钟的数值保证实机精确运行分钟数，更不能宣称全天运行。

池耗尽后不再创建新握手材料，旧认证会话仅在有效期内继续；会话过期或实验deadline后关闭外部转发。第一版不动态补池，不自动循环复用旧镜像，不通过重置计数器延长密钥寿命。需要再次使用时，主机重新生成材料并引导，期间业务会中断。DNS、IPv6旁路和多客户端策略仍按实机验收结果声明，不扩大能力范围。

## 主机引导器的阶段

| 阶段 | 必须完成的工作 | 失败处理 |
|---|---|---|
| 只读预检 | 精确USB接口/endpoint拓扑、UV310项目身份、原厂Wi-Fi/DHCP/蜂窝基线、stock尺寸与SHA；不改变Mac默认路由 | 停止，不写设备，不转向同VID/PID其他设备 |
| 准备材料 | 首次从用户管理页建立专用peer；私有配置保存在Git忽略目录；每次引导重新由主机OS CSPRNG生成池及新时间基值 | 配置不支持、主机时间回退或随机源失败时不构建 |
| 编译审计 | 从新候选构建，审计实际地址、section/heap边界、私有常量影响、stock哈希和允许补丁位置；不上传ELF/镜像 | 任何超限或版本不符均停止 |
| 单次引导 | 给本次尝试分配唯一记录，写设备前持久标记已消耗；仅部署到已确认设备 | 失败尝试也不复用该材料，不盲目重复重启 |
| 恢复持久文件 | 借鉴历史实验：候选加载后尽快把EFS活动文件恢复成原厂，并完整读回校验；候选只留在当前RAM运行 | 无法恢复时停止业务验收，按恢复手册处理 |
| 运行验收 | 用N1观察器读状态；独立Wi-Fi客户端验证DHCP DNS、真实出口、握手/换钥、UDP和资源变化 | 关闭实验并保留失败记录；不将收到状态页等同于VPN成功 |
| 再次引导 | 重新预检、重新准备材料、重新记录；不重用旧一次性镜像 | 不提供未经验证的无限自动重启循环 |

长期WireGuard身份密钥与每次握手随机材料不是同一回事。首次建立的专用peer可以按正常WireGuard身份生命周期管理；不能复用的是旧引导的随机池、时间基值和已运行的带材料镜像。当前历史真实peer是否仍有效未知，首次新实机验收应建立并核对专用peer，不从聊天记录恢复旧密钥直接使用。

时间基值应来自可信主机时钟。引导器需为peer保留私有的已签发时间/尝试状态，并用锁和持久写入处理并发与崩溃；主机时钟回退时停止并校准，不靠任意推高未来时间蒙混过关。预备记录、消耗记录的边界必须覆盖USB写入前的失败窗口。这些机制尚未写入新的统一引导器。

## 一个不能省略的恢复风险

历史方法通过EFS临时活动镜像加载候选，之后恢复stock；它不等于纯RAM下载。写入候选到恢复stock之间如果掉电或启动失败，持久存储可能仍是带一次性材料的候选，设备可能再次加载它。主机的“已消耗”记录不能阻止设备自行重启。第一版必须保留这个风险、验证读回和恢复路径，不能称为掉电安全。若无法保证恢复，不应开放自动启动；优先调查是否能使用已证实的非持久加载路径。

## 现有可复用部分

- 独立候选：[native.c](../work/uv310-wireguard/rekey-dns-observe/native.c)；`make test-dns-observe`是离线入口。
- 观察器：`observe.py --protocol n1`，仅用于硬件可用且已确认身份后读取；详见[协议文档](DNS_TELEMETRY.md)。
- 原厂恢复事实、镜像哈希与路径见[恢复文档](RECOVERY.md)。
- 旧`rekey-live/package.py`证明存在主机生成材料、链接和stock补丁的历史流程，但它硬编码旧配置、旧分支和容量，且生成部署脚本。**不能直接执行它来部署新候选。** 新引导器需要参数化、独立预检和针对当前源码的验证。

当前交付是候选源码、可重复离线验收与主机引导设计，并非已经能一条命令启动VPN的产品。缺少的新引导器应分成`prepare/check`（不访问设备）、`preflight`（只读设备）、`boot`（单次写入/恢复）和`observe`，使离线部分可在硬件缺席时先实现和测试。第一版不增加静默后台自动刷写。

## 半成品验收标准

1. 首次专用peer配置可用，主机每次生成全新单次材料；私钥与生成镜像不进入Git或公开日志。
2. 真实设备内完成握手及至少两次换钥；Wi-Fi客户端DNS与实际出口通过，主机没有代替设备的VPN。
3. 当前实验窗口内记录UDP收发、丢包和资源变化，不把ping或QEMU性能当作真实吞吐。
4. deadline/池耗尽/peer失败时按设计关闭外部转发，状态与错误可观察；再次引导不会复用旧材料。
5. 能恢复到原厂，记录临时持久写入窗口的恢复行为；未验证的断电情况如实保留。

无硬件时不能完成第2–5项。主机引导允许先绕开设备原生熵桥与自主启动的开发，但不能绕开链路、稳定性和恢复验收。

## 用户补充：允许延长renew间隔

用户接受较长的renew间隔，希望减少主机干预。需要区分长期身份密钥、协议会话密钥和主机引导材料：现有实现REKEY_AFTER_TIME=120秒、REJECT_AFTER_TIME=180秒；仅修改设备本地计时无法让标准对端接受已经过期的会话。参见[WireGuard协议说明](https://www.wireguard.com/protocol/)。当前不修改这些协议常量。

优先工程路线调整为：主机每次引导提供新高质量种子，设备用经过验证的密码学随机生成器供给本次运行的后续握手，减少对固定随机池容量的依赖，同时保留标准会话换钥。这个方案尚未实现；不能拿普通PRNG或把旧池循环使用来替代。必须检查算法实现/测试向量、状态独占与同步、输出计数耗尽、状态擦除、重启/回滚防重用，以及实际链接和峰值内存成本。

固定新种子不意味着无限期或完整的重新播种能力；状态泄露恢复与持久镜像中的种子暴露也需要单独评估。当前短时实验deadline仍保留。只有先解决上次换钥附近失联和新生成器的实机稳定性，才能逐步延长运行窗口。近期半成品目标因此是“主机单次引导后尽量长时间在网卡内运行”，不是要求用户每两分钟重新输入key。
